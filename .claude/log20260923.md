# 2026-09-23 新サーバー（Brow-eyelid-segmentation/server）接続対応：アプリ側

## 背景
新サーバーに接続すると 401「invalid or missing X-API-Key」や「応答のデコードに失敗」が出た。
サーバー側に仕様違反（`/images` の形、`/images/{id}/meta` のキー、`/status` の時刻型）がある一方で、
アプリ側にも次の弱点があったため、アプリ側でできる対応を行った。

## 変更
1. `Services/HIL/HILServerClient.swift`
   - APIキーの前後の空白・改行を削除（`normalizeAPIKey`）
   - base URL の前後の空白と末尾の `/` を削除（`normalizeBaseURL`、`//info` になるのを防止）
   - `postConfig` がレスポンス `ConfigResponse { status?, warning? }` を返すように変更
   - デコード失敗時のメッセージに keyNotFound / typeMismatch とキーのパスを表示（`HILError.describeDecodingError`）
2. `ViewModels/CanvasViewModel.swift`
   - `static var maskPalette: [[Int]]` を追加（class 1-8 の RGB）
3. `ViewModels/HILViewModel.swift`
   - `/info` の成功後に `registerConfig(info:)` で `POST /config` を送信（仕様 §7.2 の実装漏れ）
   - **クラスの数と名前はサーバーの `/info` をそのまま使い、色は iPad のパレットをクラス番号で対応させる**
     - palette = [白] + maskPalette[0 ..< num_classes-1]、class_names = info.classNames
     - クラス数が iPad の 8 色を超える場合は送らずにエラー表示
   - 失敗・warning は errorMessage に表示するだけで、接続は続行する

## 設計判断（途中で変更）
- 最初は iPad のクラス名を送る実装にしたが、「クラス1を `brow` と名付ける」という利用者の設定が必要になり、煩雑なので撤回
  （Dashboard / MainView への classNames の受け渡しも元に戻した）
- 役割分担: **クラスの定義（数・名前）= サーバー、色 = iPad**。利用者の設定は不要

## 確認
- `xcodebuild -target AnnottyHIL -sdk iphonesimulator` BUILD SUCCEEDED

# 2026-09-24 プロトコル v1.1 改訂・提出マスク修正・適合テスト追加

## 背景
LLM に作らせた新サーバーが仕様と違う形を返した。調べると、仕様書まわりに矛盾や古い情報が残っていた。
- `server/`（仕様書では参照実装）は旧網膜血管サーバーからの移行が途中。`/infer` は `run_inference(palette=...)` の引数が合わず必ず失敗する。出力は赤 RGBA。`/info` は `/config` の前だと `num_classes: 0` を返す
- `server/scripts/test_api.py` とルートの README の API 表が v1 以前の形（`{"images":[{"id":..}]}`）のまま。新サーバーの誤った形と一致しており、LLM がこれをお手本にした可能性が高い
- iPad の `exportMaskForServer` が §5.1 に違反していた（512×512 固定・全クラス赤・背景透明）

ユーザーの決定: `server/` は参照実装から外す（コードは残す）。

## 変更
1. `ViewModels/CanvasViewModel.swift` `exportMaskForServer()`
   - 既存の `resizeMask`（最近傍）で `textureManager.imageSize` にリサイズ → 既存の `createColoredPNG`（白背景・クラス色）で PNG 化。重複していた CGContext のコードを削除
2. `docs/protocol.md` を v1.1 に改訂（全面的に書き直し。通信形式は変えない）
   - §2.1 互換性ルールを新設（必須フィールドの改名・構造変更は禁止、フィールドの追加は自由、完成の条件は適合テスト全 PASS）
   - §5.2 クラス定義はサーバー、palette はクライアントと役割を分け、クラス番号で対応させる（名前で判定しない）。iPad パレット表を掲載
   - §7.2 `/config` はクラス定義が一致すれば palette を無条件で採用（不一致は 409）。`warning` を任意フィールドとして定義
   - すべてのレスポンスに必須/型の表を追加。§5.1 のサイズを「入力画像と同じ」に確定。§5.4 に日時の例外（UNIX 秒）を明記
   - `/infer` はクエリなしで動作すること、CoreML は任意機能（404 / 501）、認証キーは前後の空白を除いて比較
   - 誤った参照（§7.10）、古い用語（`completed_count`）、legacy グレースケールの規定を削除。変更履歴の過去の行は元のまま残した
3. `docs/conformance_test.py`（新規・標準ライブラリのみ）
   - 必須キーと型を `HILServerClient.swift` の Codable 構造体と一致させて検査。PNG のサイズは IHDR から読む
   - `/images` が壊れていても `/next` の ID で画像単位の検査を続ける。`--submit IMAGE_ID` を指定したときだけ書き込み検査をする
4. `server/scripts/test_api.py` を削除。`server/README.md` に「非準拠の旧実装」の注意書きを入れ、古い API 表・シーケンス図・データ構造の節を削除。ルートの `README.md` の API 表を `docs/protocol.md` への参照に置き換えた
5. `HILServerClient.swift` のヘッダーコメントを「protocol v1 (currently 1.1)」に変更

## 確認
- xcodebuild（iphonesimulator）BUILD SUCCEEDED
- スクラッチパッドのスタブで適合テストを検証: 仕様どおりのスタブは ALL PASS。新サーバーと同じ誤りを入れたスタブでは `/images`・`/meta`・`/next`・`/labels` のサイズ・`/infer` のクエリ必須・`started_at` の型・`/submit` の `status` をすべて FAIL として検出
- `protocol.md` の節番号の参照がすべて実在する節を指していること、古い用語が残っていないことを grep で確認

# 2026-09-24 (3) リモートとの統合・参照サーバーの v1.1 対応

## 背景
push しようとしたところ、リモートに未取得の 4 コミットがあった（PR #1, #2）。
- `server/` が PeriorbitAI 版の新しい多クラス対応サーバーに置き換わっていた（v1 の形に準拠）
- 仕様 rev3（ラベルを表示解像度に事前拡大するガイドライン、`smooth_labels.py`）が追加されていた
(1)(2) で `server/` を「非準拠の旧実装」として `legacy-server/` に改名したのは、手元の古い `server/` を見て判断したもので、リモートの新サーバーには当てはまらない。

## ユーザーの決定
- リモートを基準に統合する。`server/` は参照実装として残す
- クラス定義はサーバーが持つ（v1.1 の方針を維持）

## 作業
- 手元の main をバックアップ（`backup/local-main-20260924`）し、`integrate` ブランチ（origin/main から作成）にブラシ修正を cherry-pick した。`log20260501.md` の add/add 衝突は両方の内容を残して解消
- HIL 関連（iPad クライアント、`protocol/`、README、knowledge、ログ）をバックアップから取り込んだ。改名・`server/README` の書き換えは取り込まなかった
- 参照サーバー（`server/`）を v1.1 に対応させた
  - `PROTOCOL_VERSION = "1.1"`。`data/client_config.json`（クラス定義）がなければ起動時にエラー
  - `/config`: クラス定義が不一致なら 409。palette は無条件で採用（保存はクラスIDなので 409 は不要）
  - `/labels`: ディスクのラベルは常にクラスIDとして読み（`dataset.py` と同じ解釈）、採用中の palette で塗って返す
  - `/submit`（`data_manager.submit`）: RGBA は α を捨てる。「R=G=B ならクラスID」の分岐を削除（真っ白なマスクが 400 になっていた）
  - `derive_palette_from_labels.py` の既定パレットを iPad パレットに変更（背景が黒だった）
  - 動かない旧スクリプト `generate_dummy_data.py`・`migrate_data.py` と、適合テストで置き換わる `test_api.py` を削除
  - `server/README.md` を実装に合わせて書き直した（旧プール名、存在しないスクリプト、黒背景などの記述を削除）
- 仕様: rev3 を §5.1（返すマスクは表示解像度も可）と §9-8 に要約して取り込んだ。パレットにない色を含む提出は 400 に統一。§11 の参照実装に `server/` を戻した
- 適合テスト: 提出の検査で iPad と同じ RGBA を送るようにした。返すマスクは表示解像度も合格にした
- 変更履歴（`.claude/protocol-changelog.md`）に rev3 の行を原文のまま追加し、1.1 の行を更新

## 確認
- スクラッチパッドに参照サーバーのコピーとダミーデータ（fixed を含む）を用意して適合テストを実行
  - 修正前: `POST /config` が 409（fixed にデータがあるため）、`PUT /submit`（RGBA）が 400 → 2 FAIL
  - 修正後: `--submit` を含めて ALL PASS
- iPad と同じ形式のマスク（RGBA・赤い領域 20×40）を提出して `/labels` で再取得 → 赤の画素数 800 で一致。fixed のラベルも iPad のパレットで返ることを確認
- クラス定義がないときに、起動時に RuntimeError でファイルの場所と形式を示して止まることを確認
